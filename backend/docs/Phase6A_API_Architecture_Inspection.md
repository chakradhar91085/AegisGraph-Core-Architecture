# Phase 6A — API Architecture Inspection and Planning

## 1. Current Application Architecture
The AegisGraph backend is built on **FastAPI**. It is structured in a modular fashion, separating concerns into discrete services:
- **GraphRAGService**: The central orchestrator that coordinates security, retrieval, and LLM generation.
- **AegisSecurityService**: Handles continuous behavioral telemetry calculation, EWMA tracking, and risk assessment.
- **PolicyEngine**: Calculates adaptive $k_{eff}$ (context limit) and $d_{eff}$ (graph depth limit).
- **RetrievalService**: Classifies intent, resolves entities, and executes parameterized Cypher queries against Neo4j.
- **SessionStore**: Manages in-memory state for user sessions and historical queries.

## 2. Existing API Endpoints

### 1. Chat Endpoint
- **Method**: `POST`
- **Route**: `/api/v1/chat`
- **Request Schema**: `ChatRequest` (contains `query: str`)
- **Response Schema**: `ChatResponse` (contains `answer`, `session_id`, `intent`, `retrieval`, `telemetry`, `status`)
- **Service Called**: `graph_rag_service.generate_answer`

### 2. Direct Retrieval Endpoint
- **Method**: `POST`
- **Route**: `/api/v1/retrieval/query`
- **Request Schema**: `RetrievalRequest` (contains `query`, `limit`, `max_depth`)
- **Response Schema**: `RetrievalResponse`
- **Service Called**: `retrieval_service.execute`

### 3. Health Endpoints
- **Method**: `GET`
- **Routes**: `/api/v1/health`, `/api/v1/health/neo4j`, `/api/v1/health/ollama`
- **Service Called**: Direct system health checks.

## 3. Current Query Execution Flow
Tracing a standard query passing through `POST /api/v1/chat`:
1. **API Layer**: Request received. A **new `session_id`** is currently randomly generated by the route handler for every request.
2. **GraphRAGService**: Orchestrator takes over.
3. **Security Pre-Retrieval**: `aegis_security.observe_query` calculates semantic drift, calculates adaptive policy constraints ($k_{eff}$, $d_{eff}$) from the *previous* query's risk, and cleans up old history.
4. **Retrieval**: `RetrievalRequest` is created using the policy-enforced limits and passed to `RetrievalService`.
5. **Database**: `RetrievalService` executes intent classification and Neo4j Cypher.
6. **Security Post-Retrieval**: `aegis_security.calculate_risk` calculates remaining signals (temporal, entity, graph), updates instantaneous/EWMA risk, and commits the state.
7. **Generation**: If not blocked, the `ContextBuilder` formats the Neo4j records, passing them to the Ollama LLM.
8. **API Layer**: `ChatResponse` is returned containing the LLM answer and the rich `telemetry` dict.

## 4. Components Not Yet Exposed to the API
Currently, the backend *does* expose almost all internal data (intent, limits, signals, EWMA risk, blocked status) because `GraphRAGService` faithfully attaches the `TelemetryEvent` object to the final response. 

However, the following critical capability is **missing**:
- **Session Continuity**: Because the FastAPI route handler `chat_endpoint` contains `session_id = str(uuid.uuid4())`, it is impossible for an external API client to submit a sequence of queries under the same session. Therefore, risk cannot accumulate across API requests.

## 5. Recommended API Contract for AegisGraph
To support the Phase 6 frontend, the API surface must be minimally adjusted. No complex new microservices are needed.

1. **Update `POST /api/v1/chat`**
   - **Purpose**: Primary conversational endpoint.
   - **Request Model**: `ChatRequest(query: str, session_id: Optional[str] = None)`
   - **Response Model**: `ChatResponse` (existing)
   - **Service**: `GraphRAGService`

2. **(Optional) Add `GET /api/v1/session/{session_id}/telemetry`**
   - **Purpose**: Allows a frontend dashboard to re-fetch or poll current session state without submitting a query.
   - **Request Model**: Path parameter `session_id`
   - **Response Model**: `SessionState` representation
   - **Service**: `session_store.get_or_create_session`

3. **Deprecate/Hide `POST /api/v1/retrieval/query`**
   - **Purpose**: Prevent external API bypass of the security layer.

## 6. Frontend Data Requirements
To build a compelling visual demonstration, the frontend will require:
1. **Normal Answering**: `answer`, `intent`.
2. **Current Risk**: `telemetry.smoothed_risk`, `telemetry.risk_level` (LOW, MEDIUM, HIGH).
3. **Signal Breakdown**: `telemetry.signals` ($S_{sem}$, $S_{temp}$, $S_{ent}$, $S_{graph}$).
4. **Policy Constraints**: `telemetry.policy` ($\kappa_t$, `effective_context_limit`, `effective_graph_depth`).
5. **Blocking/Reduction**: `retrieval.result_count`, `retrieval.records_passed_to_context_builder`, `telemetry.blocked_by_policy`.
*(Note: All of these are already successfully serialized in the `telemetry` dictionary currently returned by `GraphRAGService`).*

## 7. Architecture Risks or Gaps
1. **Critical Session-State Issue**: The hardcoded UUID generation in `app/api/chat.py` destroys session continuity. A frontend client cannot accumulate EWMA risk over multiple queries.
2. **API Bypass Possibility**: The `POST /api/v1/retrieval/query` endpoint is publicly exposed and maps directly to `RetrievalService`. A malicious actor could bypass AegisGraph completely by calling this endpoint instead of `/chat`.
3. **In-Memory State Loss**: `session_store` is purely in-memory. Restarting the FastAPI server clears all EWMA progression. (Acceptable for a prototype, but must be documented for the frontend developer).

## 8. Recommended Phase 6A Implementation Plan
The next sequential step requires minimal code changes:
1. Modify `app/api/chat.py` to add an optional `session_id` to the `ChatRequest` schema.
2. Update the `chat_endpoint` function logic: use the provided `session_id` if it exists, otherwise generate a new UUID.
3. Remove or comment out the `app/api/retrieval.py` endpoint from `main.py` router registration to close the API bypass vulnerability.
4. Verify the API changes by testing via Swagger UI (`/docs`).
