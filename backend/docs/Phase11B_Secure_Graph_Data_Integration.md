# Phase 11B: Secure Graph Data Integration

## 1. Architecture Implemented
We implemented a secure backend graph projection layer. 
The new `GraphDataExtractor` intercepts the securely authorized `RetrievalResponse` generated by the `RetrievalService`. It translates the tabular database rows into a normalized `{nodes: [], edges: []}` schema, which is then attached to the `ChatResponse` sent to the frontend.

Crucially, **the backend security pipeline remains the absolute single source of truth**. The projection layer performs no new Neo4j queries and operates solely on the data already vetted by the `AdaptivePolicy`.

## 2. Graph Data Schema
The visualization payload uses a minimal, generalized graph model:

```python
class GraphNode(BaseModel):
    id: str
    label: str
    type: str

class GraphEdge(BaseModel):
    source: str
    target: str
    type: str
    weight: Optional[float] = None

class GraphVisualizationPayload(BaseModel):
    nodes: List[GraphNode]
    edges: List[GraphEdge]
```

## 3. Supported Intents
Currently, the `GraphDataExtractor` successfully projects topology for the following enriched intents:
1. **`frequent_communication`**: Maps the queried Employee to their top contacts (`Employee -> COMMUNICATES_FREQUENTLY_WITH -> Employee`).
2. **`topical_footprint`**: Maps the queried Employee to the topics they mention (`Employee -> FREQUENTLY_MENTIONS -> Entity`).
3. **`organization_info`**: Maps the queried Employee to their department/organization (`Employee -> BELONGS_TO -> Organization`).
4. **`person_connection`**: Projects the path array between two employees into individual `Employee` nodes and `COMMUNICATES_FREQUENTLY_WITH` edges.

For other legacy intents (like `sent_emails` or generic `employee_lookup`), the `graph_data` returns empty arrays, as there is no meaningful graph topology to project safely without querying additional neighbors.

## 4. Security Guarantees
- **No Unrestricted Traversal:** The projection layer uses only the `results` array of the `RetrievalResponse`. No new Cypher queries are executed.
- **Blocked Queries Protected:** If the `AdaptivePolicy` blocks a query, `results` is empty, which inherently forces `graph_data` to be empty. No protected nodes leak.
- **Restricted Retrieval Honored:** The graph projection can only render up to the `effective_context_limit` permitted by the Adaptive Policy.

## 5. Visualization Payload Cap
Even if the security policy allows retrieving 50 relationships, sending 50 nodes and 50 edges to a React Force Graph simultaneously can cause UI stuttering and visual overload. 

We introduced a **Presentation Cap (`VISUALIZATION_CAP = 25`)** inside the `GraphDataExtractor`. 
- This limits the maximum number of rows projected into graph geometry. 
- It does **not** alter the data sent to the LLM (which receives up to the true `effective_context_limit`). It strictly caps the visual rendering payload to keep the UI clean.

## 6. Testing Results
We created `tests/test_graph_extractor.py` and executed the standard regression suites (`tests/verify_backend.py` and `tests/verify_api_endpoints.py`). 
- **Unit Tests:** `test_graph_extractor.py` passed (100%), confirming that the projection layer accurately extracts nodes and edges from `frequent_communication`, `person_connection`, and empty/blocked responses.
- **Regression:** `verify_backend.py` and `verify_api_endpoints.py` both passed, proving that appending `graph_data` to the `ChatResponse` schema did not break existing frontend data parsing or LLM behavior.

## 7. Known Limitations
- The `person_connection` strategy returns an ordered array of names rather than strict `employee_id`s. The projection layer uses the names as the node `id`s for this specific visualization. While this works visually, if multiple employees share an identical name, they will merge into a single visual node.
- The projection currently only builds depth-1 star topologies for most queries (except paths). Visualizing deeper relationships relies on the user actively querying those neighboring nodes in subsequent interactions (to be implemented in Phase 11C via session accumulation).
